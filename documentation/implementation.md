# Implementation boundaries

- REST resources use JWT authentication and an authorized membership ID in `X-Property-Id`. Society data is scoped by society; household data additionally by unit. A phone number is an account, not a flat. Family membership access is managed by owners/tenants on the backend.
- Access tokens expire after 15 minutes by default. Refresh tokens are hashed, rotated, and grouped into revocable families; reuse revokes the family. OTP challenges expire, are single-use, and have attempt limits. Database-backed rate counters support multiple API workers.
- Money is integer paise. Backend payment amounts come from outstanding bills. Paid receipts are immutable payment records; duplicate success events do not debit the bill twice. Conflicting settlements are flagged for office review. Live credentials and gateway-level acceptance were not part of this development pass.
- Amenity slots are one hour, limited to the next 30 days, using India time. A transaction locks the amenity before checking overlaps. Booking fees, when configured, are payable at the society office; maintenance uses the online payment flow.
- Invitations have expiring, revocable opaque QR tokens and six-digit PINs. QR payload version 1 is `{v:1,type:"society-invitation",token:"…"}`. A future authenticated guard API must validate status, time window and society, rate-limit PIN checks, then record entry/exit. No public PIN-validation endpoint or guard application is included.
- Files accept validated JPG/PNG/WebP images and PDFs up to 10 MB. Complaint photos and profile uploads are supported; video is deferred. Document downloads are authorized, including optional owner-only documents. Notice attachment IDs refer to society documents. Before accepting untrusted uploads at public scale, add malware scanning to the storage boundary.
- In-app notifications are persisted. The Expo push adapter and device registration are implemented; delivering push requires EAS/FCM/APNs configuration. A complaint submission demonstrates post-commit push delivery. No delivery queue is introduced.
- Emergency alerts are persisted and acknowledged. They do not dispatch responders; quick-call actions remain the immediate assistance route. A guard/admin recipient workflow is outside the requested resident application.
- Staff assignments, visitor entry/exit records, notices, bills, society documents and domestic-help links are seeded for demonstration. Their administrative publishing interfaces belong to the future admin/guard apps, which are intentionally not implemented.
- English strings are organized for incremental localization. Sample privacy/terms text explicitly identifies the development status; replace it with society-specific published policies before distribution.
- The Stitch project could not be accessed. After the user authorized independent UI design, the mobile UI used a warm neutral / forest-green theme, Manrope typography, reusable cards, and five bottom tabs.

Version selection was checked against the [Expo SDK 57 release notes](https://expo.dev/changelog/sdk-57) and npm's stable package tags. The payment flow follows [Razorpay's server verification requirements](https://security.razorpay.com/security/checklist/).
