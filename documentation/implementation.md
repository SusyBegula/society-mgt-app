# Implementation boundaries

- REST resources use JWT authentication and an authorized membership ID in `X-Property-Id`. Society data is scoped by society; household data additionally by unit. A phone number is an account, not a flat. Family membership access is managed by owners/tenants on the backend.
- Access tokens expire after 15 minutes by default. Refresh tokens are hashed, rotated, and grouped into revocable families; reuse revokes the family. OTP challenges expire, are single-use, and have attempt limits. Database-backed rate counters support multiple API workers.
- Money is integer paise. Backend payment amounts come from outstanding bills. Paid receipts are immutable payment records; duplicate success events do not debit the bill twice. Conflicting settlements are flagged for office review. Live credentials and gateway-level acceptance were not part of this development pass.
- Amenity slots are one hour, limited to the next 30 days, using India time. A transaction locks the amenity before checking overlaps. Booking fees, when configured, are payable at the society office; maintenance uses the online payment flow.
- Invitations have expiring, revocable opaque QR tokens and six-digit PINs. QR payload version 1 is `{v:1,type:"society-invitation",token:"…"}`. The authenticated guard API checks society, active host, status and time at admission. Walk-ins need resident approval before a guard records entry. The guard app includes a native QR scanner and PIN fallback.
- Files accept validated JPG/PNG/WebP images and PDFs up to 10 MB. Complaint photos and profile uploads are supported; video is deferred. Document downloads are authorized, including optional owner-only documents. Notice attachment IDs refer to society documents. Before accepting untrusted uploads at public scale, add malware scanning to the storage boundary.
- Notifications are persisted and dispatched by a separate durable worker. It tracks each device, retries transient failures and checks provider receipts. New membership-specific notifications retain the originating context; revoking that membership prevents queued delivery even if the user still owns another flat. Legacy/user-level notifications have no exact property context. Native push requires EAS/FCM/APNs configuration and device testing.
- Emergency alerts support office/guard acknowledgement and resolution. They do not dispatch public emergency services. Residents retain quick-call actions.
- Society setup, flat imports, staff/resident access, billing rules, cheque clearance, credits, expenses, bank matching, refunds, resources, policies, audit history, meetings, assets and privacy requests have office interfaces. Platform subscription status is bookkeeping; automatic platform charging and subscription invoices are not implemented.
- Each society resolves its own server-side Razorpay configuration. Refunds require approval and provider reconciliation. This is not a full double-entry or statutory accounting package.
- Parcel codes are available to residents in their flat's parcel screen. Guard creation/list responses exclude codes; handover requires the resident's code. Push delivery is queued, not assumed successful at parcel creation.
- Web office pages use browser downloads and session storage. Native tokens use SecureStore. Maintenance checkout uses the native Razorpay integration; browser checkout is not implemented.
- English strings are organized for incremental localization. Sample privacy/terms text explicitly identifies the development status; replace it with society-specific published policies before distribution.
- The Stitch project could not be accessed. After the user authorized independent UI design, the mobile UI used a warm neutral / forest-green theme, Manrope typography, reusable cards, and five bottom tabs.
